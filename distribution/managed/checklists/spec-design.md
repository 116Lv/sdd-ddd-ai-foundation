# 명세·설계 검토 체크리스트

구현 전에 변경에 필요한 결정과 명세의 빈틈을 확인한다. [변경 절차](../workflow.md)를 따르고 [문서 지도](../../docs/README.md)에서 관련 원본을 찾는다.

## 공통 확인

- [ ] 변경의 목적·포함 범위·제외 범위와 행위자가 제안에 있고, 관찰할 결과가 명세에 있다.
- [ ] 적용되는 권한·업무 규칙의 판단 기준과 성공·거절 결과를 시나리오에서 확인할 수 있다.
- [ ] 용어와 규칙이 관련 원본과 일치하고, 설계에서 해당 책임을 맡는 경계와 규칙을 지키는 위치가 드러난다.
- [ ] 각 시나리오 제목에 `[AC-001]` 형식의 ID를 붙인다. 변경 전체에서 ID가 유일하며, 다른 변경의 AC는 변경 이름과 함께 참조한다.
- [ ] `tasks.md`의 구현·검증 작업은 `(AC: AC-001)`처럼 인수 조건과 연결한다. 명세 외 환경 준비는 `(SETUP: 사유)`를 사용한다.
- [ ] 설계에 영향 범위, 중요한 선택의 이유와 검증 방법을 기록했다.
- [ ] 구현에 영향을 주는 미정 사항과 필요한 결정을 기록했다.

OpenSpec 시나리오 표기 예시

```markdown
### Requirement: <요구사항 이름>
<관찰 가능한 요구 동작을 SHALL 또는 MUST와 함께 작성>

#### Scenario: [AC-001] <시나리오 이름>
- **WHEN** <조건과 행위>
- **THEN** <관찰할 결과>
```

## 변경에 해당할 때 확인

- [ ] 상태 변경에 허용·금지 전이와 전이 후 결과가 있다.
- [ ] 중복 요청, 동시 변경, 외부 실패가 일어날 수 있으면 중복 효과, 부분 실패 후 상태와 복구 방법을 다뤘다.
- [ ] 계약이나 데이터가 바뀌면 영향받는 소비자, 호환성, 전환 방법을 확인했다.

각 발견 사항의 문서 위치, 분류, 영향, 필요한 결정이나 수정 내용을 남긴다. 검토 방식은 [프로젝트 설정](../../docs/project/profile.md)을 따른다.
