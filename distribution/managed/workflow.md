# 기능 변경 절차

도구 준비와 단계별 명령은 [첫 변경을 여는 방법](getting-started.md)에서 확인한다. 첫 기능은 [제품 개요](../docs/product/brief.md)의 출시 범위에서 고른다. 기능을 추가하거나 변경할 때는 관련 [도메인 용어](../docs/domain/glossary.md), [프로젝트 설정](../docs/project/profile.md)을 확인한다. 해당 기능의 현재 명세가 있으면 함께 읽는다.

1. **제안과 명세.** OpenSpec의 변경 `proposal.md`에 목적, 포함 범위, 제외 범위, 행위자와 권한, 미정 사항을 기록한다. 변경의 `specs/`에는 정상·실패 시나리오와 관찰 가능한 결과를 적는다. 시나리오 제목에 `[AC-001]` 형식의 인수 조건 ID를 붙이고 변경 안에서 중복 없이 사용한다. 다른 변경의 인수 조건을 참조할 때는 변경 이름을 함께 적는다.
2. **설계.** 변경의 `design.md`에 관련 도메인 경계와 책임, 업무 규칙이 적용되는 위치를 적는다. 필요한 경우 상태 전이, 데이터, 계약, 권한, 동시성, 중복 요청, 외부 실패와 호환성 영향을 다룬다. 공통 규칙과 상세 계약은 [프로젝트 문서 지도](../docs/README.md)의 원본을 연결한다.
3. **작업과 검토.** OpenSpec의 `tasks.md`에 구현과 검증 작업을 적고 `(AC: AC-001)`처럼 명세와 연결한다. 환경 준비에는 `(SETUP: 사유)`를 쓴다. 구현 전에 기대 동작의 모호함, 규칙 충돌과 구현에 영향을 주는 미정 사항을 해소한다. 검토는 프로젝트 설정을 따른다.
4. **구현과 검증.** 명세와 설계에 맞춰 구현하고 프로젝트 설정에서 정한 방법으로 확인한다. 명세와 구현이 어긋나면 의도한 변경인지 구현 오류인지 판단하고 해당 원본을 바로잡는다. 각 인수 조건의 충족·미충족·미검증 상태, 검증 방법과 결과, 증거 위치, 남은 문제를 PR·CI에 연결한다. PR을 쓰지 않는 경우 변경 폴더의 `verification.md`에 남긴다.
5. **마무리.** 모든 인수 조건의 충족을 확인하면 OpenSpec 절차로 현재 명세에 반영하고 완료한 변경 기록을 보관한다. 구현·검증·배포의 실제 결과를 각 단계에 기록한다. 인계할 때는 변경 이름, 관련 브랜치나 커밋, 남은 작업과 검증 증거 위치를 전달한다.

사소한 문구 수정은 영향 범위와 필요한 검증을 기록하는 수준으로 진행해도 된다. 동작·권한·계약이 바뀌는 경우 해당 명세와 인수 조건을 갱신한다.

## 문서 구조 검사

프로젝트 루트에서 Node.js 22.20.0 이상으로 실행한다.

```sh
node .foundation/checks/cli.mjs
node .foundation/checks/cli.mjs --change reserve-product --json
```

첫 명령은 시작 문서의 필수 파일·항목과 링크를 검사한다. 시작 문서의 `미정`은 기록할 항목이 있다는 뜻으로 허용한다. 두 번째 명령은 선택한 변경의 `proposal.md`, `specs/<기능>/spec.md`, `tasks.md`를 검사한다. 기능 경로는 여러 디렉터리로 구성할 수 있다. `spec.md`가 있는 기능 아래에서는 실제 하위 `spec.md`만 검사한다. 그 외의 말단 디렉터리에는 `spec.md`가 필요하다. 다른 위치에서 실행할 때는 `--project-root <폴더>`를 지정한다. 종료 코드는 통과 0, 발견 사항 1, 입력·환경 오류 2다. `--json`을 지정하면 결과와 발견 사항을 JSON으로 출력한다.

제안에는 아래 2단계 제목과 내용을 적는다. 기본 OpenSpec 양식에서는 영어 제목을 유지한다. 한국어로 작성한 기존 제안에서는 표의 한국어 제목도 인식한다.

| 기본 제목 | 한국어 제목 |
|---|---|
| Why | 목적 |
| What Changes | 포함 범위 |
| Capabilities | 기능 |
| Impact | 영향 |
| Out of Scope | 제외 범위 |
| Actors and Permissions | 행위자와 권한 |
| Open Questions | 미정 사항 |

명세에서 `#### Scenario: [AC-001] 이름` 형태의 제목과 `- **WHEN** 조건`, `- **THEN** 결과`를 검사한다. 변경 안에서 AC ID는 한 번만 정의한다. 작업 체크박스에서 `(AC: AC-001)` 또는 쉼표로 나열한 ID를 사용해 각 시나리오를 작업에 연결한다. 준비 작업에는 `(SETUP: 사유)`를 쓴다. 기능 명세가 필요 없는 변경은 해당 변경 폴더의 `.openspec.yaml`에 들여쓰기 없이 `skip_specs: true`를 적을 수 있다. 이 검사는 따옴표 없는 단일 리터럴 키와 값, 선택적 줄 끝 주석을 지원한다. 이 경우 명세 파일이 없으면 기능 항목을 생략할 수 있다.

한 줄에 적은 `[설명](상대/경로.md)` 또는 `[설명](<공백 있는 경로.md> "제목")` 형식의 링크를 검사한다. 퍼센트 인코딩된 경로를 해석하며 파일이나 폴더의 존재를 확인할 때 경로 뒤의 프래그먼트와 쿼리는 생략한다. URL, 앵커만 있는 링크, 참조형 링크, 이미지, 여러 줄에 걸친 링크, 중첩된 괄호·대괄호, 코드 블록·코드 span·HTML 주석의 예시는 검사 범위에서 제외한다. 절대 파일 경로, 프로젝트 밖으로 벗어나는 상대 경로, 심볼릭 링크를 거치는 파일 경로는 외부 의존 참조로 보고한다.

통과 결과는 필수 항목과 참조 구조에 대한 것이다. 공식 OpenSpec 문법, 정상·실패 흐름의 충분성, 권한과 업무 규칙, 구현·검증 결과는 각 검토 단계에서 확인한다.
