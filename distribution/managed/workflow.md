# 기능 변경 절차

첫 기능은 [제품 개요](../docs/product/brief.md)의 출시 범위에서 고른다. 기능을 추가하거나 변경할 때는 관련 [도메인 용어](../docs/domain/glossary.md), [프로젝트 설정](../docs/project/profile.md)을 확인한다. 해당 기능의 현재 명세가 있으면 함께 읽는다.

1. **제안과 명세.** OpenSpec의 변경 `proposal.md`에 목적, 포함 범위, 제외 범위, 행위자와 권한, 미정 사항을 기록한다. 변경의 `specs/`에는 정상·실패 시나리오와 관찰 가능한 결과를 적는다. 시나리오 제목에 `[AC-001]` 형식의 인수 조건 ID를 붙이고 변경 안에서 중복 없이 사용한다. 다른 변경의 인수 조건을 참조할 때는 변경 이름을 함께 적는다.
2. **설계.** 변경의 `design.md`에 관련 도메인 경계와 책임, 업무 규칙이 적용되는 위치를 적는다. 필요한 경우 상태 전이, 데이터, 계약, 권한, 동시성, 중복 요청, 외부 실패와 호환성 영향을 다룬다. 공통 규칙과 상세 계약은 [프로젝트 문서 지도](../docs/README.md)의 원본을 연결한다.
3. **작업과 검토.** OpenSpec의 `tasks.md`에 구현과 검증 작업을 적고 `(AC: AC-001)`처럼 명세와 연결한다. 환경 준비에는 `(SETUP: 사유)`를 쓴다. 구현 전에 기대 동작의 모호함, 규칙 충돌과 구현에 영향을 주는 미정 사항을 해소한다. 검토는 프로젝트 설정을 따른다.
4. **구현과 검증.** 명세와 설계에 맞춰 구현하고 프로젝트 설정에서 정한 방법으로 확인한다. 명세와 구현이 어긋나면 의도한 변경인지 구현 오류인지 판단하고 해당 원본을 바로잡는다. 각 인수 조건의 충족·미충족·미검증 상태, 검증 방법과 결과, 증거 위치, 남은 문제를 PR·CI에 연결한다. PR을 쓰지 않는 경우 변경 폴더의 `verification.md`에 남긴다.
5. **마무리.** 모든 인수 조건의 충족을 확인하면 OpenSpec 절차로 현재 명세에 반영하고 완료한 변경 기록을 보관한다. 구현·검증·배포의 실제 결과를 각 단계에 기록한다. 인계할 때는 변경 이름, 관련 브랜치나 커밋, 남은 작업과 검증 증거 위치를 전달한다.

사소한 문구 수정은 영향 범위와 필요한 검증을 기록하는 수준으로 진행해도 된다. 동작·권한·계약이 바뀌는 경우 해당 명세와 인수 조건을 갱신한다.
