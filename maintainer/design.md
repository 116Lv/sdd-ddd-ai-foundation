# 재사용 가능한 SDD 개발 기반 — 구조 설계 초안

- 상태: Draft — 구조 검토용, 구현 전
- 버전: 0.2
- 작성일: 2026-11-18
- 기준: [요구사항 초안 v0.2](requirements.md)
- 성격: 솔루션 제작용 문서. 새 프로젝트에 기본 제공하는 문서가 아니다.
- 표시 원칙: 사용자와 합의한 목적을 구현하기 위한 아래 파일 구조·전달 방식·운영 세부는 설계 제안이다.

## 1. 이번 설계의 핵심

원본 저장소는 솔루션을 만드는 곳으로 유지한다. 새 프로젝트에는 공통 규칙·양식·안내·검사 도구만 제공한다. 새 프로젝트의 실제 기획·명세·코드·배포 설정은 그 프로젝트가 소유한다.

SDD가 전체 작업 흐름의 중심이다. DDD는 명세와 설계에서 필요한 업무 개념·규칙·책임을 정리하는 데 사용한다. DDD 문서 전체를 먼저 완성하도록 강제하지 않는다.

예를 들어 예약 서비스를 시작할 때, 이 솔루션을 만들었던 요구사항은 가져가지 않는다. 빈 기획 양식과 작업 원칙을 가져가 예약 서비스의 목적·도메인·명세를 작성한다.

## 2. 비교한 전달 방식

| 방식 | 장점 | 비용·제약 | 이번 제안 |
|---|---|---|---|
| 원본 전체 Fork | GitHub에서 바로 시작하고 원본 이력을 유지 | 제작 자료까지 포함되며 제품 내용과 원본 변경이 섞일 수 있음 | 원본 솔루션의 개선·기여에 적합. 제품 시작 시 기본 제공 경로로 삼지 않음 |
| 원본 전체를 GitHub Template로 사용 | 새 프로젝트를 독립 저장소로 시작 | 원본 전체를 템플릿으로 삼으면 제작 자료도 전달됨 | 원본에 바로 적용하지 않음 |
| 사용할 구성만 내보내기 | 제작 자료를 제외하고 파일 소유 경계를 분명하게 유지 | 내보내기·버전 기록·업데이트 안내가 필요 | 초기 추천안 |

GitHub의 Template 기능은 템플릿 저장소의 구조와 파일을 복제하는 방식이다. 원본 저장소의 특정 하위 폴더만 자동 선택해 주는 기능으로 가정하지 않는다.

초기에는 내보낸 프로젝트 시작용 압축 파일을 GitHub Release에 제공하는 방식을 제안한다. 사용자는 빈 폴더에 압축을 풀고 새 GitHub 저장소에 올린다. 추후 필요하면 같은 내보내기 결과를 별도 Template 저장소로 제공할 수 있지만 초기 필수 범위에는 넣지 않는다.

원본 개선은 Fork 전체 동기화 대신 공통 구성의 버전 업데이트로 가져온다. 자동 업데이트 서비스나 별도의 패키지 저장소는 만들지 않는다.

## 3. 원본 저장소 구조 제안

```text
foundation-source/
├─ README.md                         # 이 솔루션의 소개·사용·기여 안내
├─ AGENTS.md                         # 솔루션 자체를 개발할 때의 지침
├─ maintainer/
│  ├─ requirements.md                # 이 솔루션의 요구사항
│  ├─ design.md                      # 이 솔루션의 설계
│  ├─ decisions/                     # 유지관리상 중요한 결정
│  └─ verification/                  # 솔루션 검증 기록
├─ distribution/
│  ├─ managed/                       # 새 프로젝트의 .foundation/에 전달
│  │  ├─ guide.md
│  │  ├─ workflow.md
│  │  ├─ skills/                      # 도구 공통의 추가 검토 스킬 원본
│  │  ├─ checklists/
│  │  ├─ templates/
│  │  └─ checks/
│  └─ starter/                       # 시작할 때 한 번 생성하는 파일의 원본
│     ├─ README.md.template
│     ├─ AGENTS.md.template
│     ├─ CONTRIBUTING.md.template
│     └─ docs/
├─ integrations/                     # AI 도구별 연결 양식·생성 규칙·검증 정보
├─ examples/                         # 참고 전용 사례, 기본 배포물에서 제외
├─ tools/                            # 내보내기·업데이트 비교 도구
├─ tests/                            # 도구·배포물·문서 검사 검증
├─ releases/                         # 버전별 제공 파일 목록·적용 안내
├─ CHANGELOG.md
└─ LICENSE
```

실제 원본 저장소에는 OpenSpec을 사용해 이 솔루션을 개발하는 기록도 생길 수 있다. 이는 유지관리 영역이며 배포물에는 포함하지 않는다. 배포는 저장소 전체 복사가 아니라 명시한 파일 목록만 내보내는 방식으로 한다.

`*.template` 파일은 새 프로젝트에 전달할 때 실제 이름으로 생성한다. 원본을 관리하는 AI가 템플릿 내부의 프로젝트 지침을 원본 저장소의 활성 지침으로 혼동하지 않게 한다.

## 4. 새 프로젝트에서 보이는 구조

```text
my-project/
├─ README.md                         # 해당 프로젝트 소개
├─ AGENTS.md                         # 공통 지침·프로젝트 규칙의 진입점
├─ CONTRIBUTING.md                   # 해당 프로젝트의 기여·리뷰 절차
├─ .foundation/                      # 버전별 공통 구성
│  ├─ guide.md
│  ├─ workflow.md
│  ├─ skills/                        # 공통 검토 스킬의 버전 관리 원본
│  ├─ checklists/
│  ├─ templates/
│  └─ checks/
├─ foundation.lock.json              # 기반 버전·관리 파일 목록·기준 해시
├─ docs/
│  ├─ README.md                      # 해당 프로젝트의 문서 지도
│  ├─ project/
│  │  └─ profile.md                  # 기술·명령·코드 규칙·검토 방식
│  ├─ product/
│  │  └─ brief.md                    # 문제·사용자·성공 기준·범위·미정 사항
│  ├─ domain/
│  │  └─ glossary.md                 # 실제 업무 용어
│  ├─ architecture/                  # 필요할 때 실제 설계를 작성
│  ├─ adr/
│  └─ runbooks/
├─ contracts/                        # 필요할 때 실제 API·이벤트 계약 작성
└─ openspec/                         # 선택한 AI 도구에 맞춰 초기화
   ├─ config.yaml
   ├─ specs/
   └─ changes/
      └─ archive/
```

AI 도구를 선택하면 위 기본 구조에 그 도구가 읽는 진입·스킬 연결 파일을 추가한다. 공통 스킬은 한곳에서 관리하고, 실제 인식 경로에는 도구가 지원하는 링크·가져오기·생성 복사본 중 검증한 방식을 사용한다. 따라서 AI별 연결 경로가 기본 구조도에 없다고 해서 연결 파일 없이 사용할 수 있다는 뜻은 아니다. 구체적인 사용 후 예시는 10절에 정리한다.

처음부터 모든 빈 폴더와 문서를 생성하지 않는다. 초기 필수 파일은 진입 문서, 프로젝트 설정 양식, 제품 개요 양식, 용어집으로 한정한다. 나머지는 첫 기능과 실제 필요에 따라 생성한다.

`openspec/`는 초기 사용 안내를 따라 OpenSpec으로 초기화한다. 표시한 구조는 사용 후 모습이며, 압축 해제만으로 도구 연결이 구성됐다고 표시하지 않는다. AI별 스킬 경로도 사용 도구를 선택한 뒤 생성한다.

프론트엔드·백엔드 코드 폴더, 언어별 빌드 파일, DB·인프라·배포 설정은 기본 생성하지 않는다. `contracts/`도 실제 계약이 필요할 때 만든다.

## 5. 파일 소유 경계

| 구분 | 소유자 | 수정·업데이트 방식 |
|---|---|---|
| `.foundation/` | 기반 제공 버전 | 직접 수정 대신 프로젝트 규칙에서 허용된 설정을 조정. 수정 흔적이 있으면 업데이트 전에 충돌로 보고 |
| `foundation.lock.json` | 기반 관리 도구 | 버전·파일 목록·기준 해시만 기록. 사람의 업무 진행 상태는 저장하지 않음 |
| 루트 진입 문서·`docs/`·`contracts/` | 해당 프로젝트 | 시작 시 생성한 이후 일반 기반 업데이트에서 덮어쓰지 않음 |
| `openspec/config.yaml`, 명세·변경 기록 | 해당 프로젝트 | OpenSpec과 프로젝트 작업 절차에 따라 관리. 기반 업데이트가 덮어쓰지 않음 |
| OpenSpec 생성 스킬·AI 연결 파일 | 도구 생성물 + 프로젝트에서 선택한 설정 | 해당 도구의 갱신 절차로 관리. 기반 규칙 파일과 구분 |

프로젝트 규칙은 공통 구성에서 명시적으로 조정 가능한 부분만 변경한다. 예를 들어 언어·실행 명령·테스트 범위·개인/팀 리뷰 방식은 프로젝트별로 정한다. 실행하지 않은 검사를 성공으로 기록하지 않는 원칙, 인수 조건과 검증을 연결하는 원칙, 사용자 변경을 보존하는 원칙은 기술 선택과 별개로 유지한다.

규칙이 충돌하면 무조건 한쪽을 우선하지 않는다. 충돌과 영향 범위를 기록하고 해당 규칙의 소유 문서에서 해결한다. AI 도구 자체의 상위 지침·권한 체계를 저장소 문서로 덮어쓸 수 있다고 가정하지 않는다.

## 6. 기획에서 기능 개발로 넘어가는 절차

| 시점 | 기록할 내용 | 주요 결과물 |
|---|---|---|
| 시작 | 제품 문제·사용자·성공 기준·첫 범위 | `docs/product/brief.md` |
| 공통 이해 | 핵심 용어·업무 흐름·필요한 경계 후보 | 용어집과 필요한 도메인 문서 |
| 기능 제안 | 왜 바꾸는지, 포함·제외 범위, 미정 사항 | OpenSpec 변경 제안 |
| 명세 | 관찰 가능한 동작·실패·권한·인수 조건 | OpenSpec 변경 명세 |
| 설계 | DDD 책임·규칙·경계, 필요한 기술·데이터·계약·검증 접근 | 변경 설계와 관련 계약 |
| 작업 | 명세를 구현·검증 작업으로 분해 | OpenSpec 작업 목록 |
| 구현·검증 | 구현 결과, 테스트, 명세와의 차이 | 변경 코드·검증 기록·PR·CI |
| 변경 완료 | 현재 명세 반영·기록 보관 | 현재 명세와 완료한 변경 기록 |
| 운영 | 배포·관측·복구, 발견한 문제 | 프로젝트 운영 문서와 후속 변경 |

기능 명세·변경 제안·설계·작업 목록은 OpenSpec 산출물을 사용한다. 같은 목적의 자체 `spec.md`·`plan.md`·진행 장부를 따로 만들지 않는다. 기획·도메인·ADR·운영 안내는 역할이 달라 별도로 둔다.

명세 검토와 중요한 미정 사항 해결은 구현 전에 수행한다. 개인은 자체 검토, 팀은 해당 프로젝트가 정한 리뷰 방식을 사용한다. 사소한 문구 수정에는 기능 개발 전체 절차를 강제하지 않는다. 동작·권한·계약이 바뀌면 관련 명세와 검증을 포함한다.

## 7. DDD 적용의 깊이

기본으로 용어와 핵심 업무 규칙을 명확하게 한다. 여러 업무 개념이 섞이거나 책임이 모호하면 경계와 관계를 설계한다. 상태를 갖는 업무에는 상태·전이·불변 조건을 정리한다.

애그리거트, 값 객체, 도메인 이벤트 등은 실제 모델에 필요할 때 설계한다. 모든 프로젝트에서 모든 항목을 채우거나 별도 서비스를 만들도록 강제하지 않는다. 적용하지 않는 항목은 명세·설계에서 짧게 이유를 남긴다.

재사용되는 업무 규칙은 도메인 문서가 원문을 소유하고 명세에서 참조한다. 기능에만 해당하는 세부 동작은 기능 명세가 소유한다. API 필드와 타입은 실제 계약 파일이 소유하며, 명세는 그 계약을 연결한다.

## 8. 같은 깊이의 결과물을 만드는 장치

1. **필수 명세 항목:** 목적·범위·행위자/권한·정상/실패 시나리오·인수 조건·미정 사항을 다룬다. 적용되지 않는 항목도 사유를 표시한다.
2. **인수 조건 식별:** 변경 안에서 안정적인 ID를 부여하고 작업·검증에서 참조한다. OpenSpec 요구사항·시나리오 형식을 보존하면서 ID 표기를 더한다. 정확한 표기는 구현 계획에서 고정한다.
3. **조건부 설계 항목:** 상태·동시성·중복·외부 실패·보안·호환성·복구는 해당할 때 다룬다.
4. **한 가지 연결된 예시:** 예약 취소 같은 작은 사례로 기획 → 규칙 → 명세 → 설계 → 작업 → 검증을 보여준다. 원본 `examples/`에서 참고하며 기본 제품 파일에는 포함하지 않는다.
5. **완료 체크리스트:** 명세와 계약 일치, 해당 검증 결과, 미실행 항목, 남은 위험을 확인한다.
6. **프로젝트 설정:** 기술 선택 이후 의존성 방향·오류 처리·코드 스타일·테스트 방식 등을 같은 문서에 연결한다.

문서 길이나 모든 팀원이 동일한 표현을 썼는지는 평가하지 않는다. 같은 동작을 설명하고 같은 완료 조건을 검증할 수 있는지가 기준이다.

## 9. 작업 상태와 검증 기록

- OpenSpec `tasks.md`: 구현·검증의 세부 체크리스트.
- Issue 또는 협업 보드: 담당자·우선순위·작업 전체의 진행 상태. 개인 프로젝트에서 외부 보드를 필수로 요구하지 않는다.
- PR·CI: 실제 변경 검토와 실행 결과의 기본 증거.
- 외부 도구 없이 사용하는 경우: 변경 폴더의 짧은 `verification.md`에 명령·결과·증거·미검증 항목을 기록한다. PR을 사용하면 같은 내용을 복제하는 대신 링크한다.

명세 승인, 구현 완료, 검증 완료, 배포 완료는 서로 다르다. 모든 작업이 체크되어도 실행 증거가 없으면 검증 완료로 처리하지 않는다. 현재 명세 반영과 기록 보관은 요구사항을 충족했는지 확인한 뒤 수행하고, 미해결 인수 조건이 있으면 완료와 구분한다.

인계는 변경 식별자와 관련 브랜치·커밋, 미완료 작업·미정 사항·검증 증거의 위치를 전달한다. 별도 영구 대화 요약이나 AI별 진행 장부는 기본으로 만들지 않는다.

## 10. OpenSpec·공통 스킬·AI 도구별 연결

### 10.1 세 층의 역할

| 층 | 담을 내용 | 유지관리 원칙 |
|---|---|---|
| 공통 기준 | 기획·DDD 설계·명세·코드 규칙·완료 조건 | 실제 프로젝트 문서가 원본. AI별로 별도 명세를 만들지 않음 |
| 공통 스킬 | 반복 작업의 입력·읽을 문서·수행 순서·결과 형식 | 한 원본으로 관리하고 공통 기준을 참조. 제품 규칙을 복제하지 않음 |
| 도구별 연결 | 각 도구가 인식하는 진입 파일·스킬 경로·메타데이터 | 도구별 인식 방식에 맞춰 제공하고 실제 적용 여부 검증 |

공통 스킬을 도구별로 전달할 때 작업 목적과 완료 기준은 유지한다. 호출 표기·인식 경로·지원 기능처럼 도구에 종속된 부분만 조정한다. 도구가 지원하지 않는 기능을 지원한다고 표현하지 않으며, 자동 호출이 불가능하면 명시적으로 실행하는 방법을 안내한다.

### 10.2 초기 스킬 범위

OpenSpec의 변경 제안·명세·설계·작업·구현·명세 반영 절차를 다시 구현하지 않는다. 공통 기준을 기존 절차에 연결하고, 결과물 편차를 줄이는 추가 검토부터 제공한다.

| 스킬 범위 | 주요 입력 | 공통 출력 |
|---|---|---|
| 명세·설계 검토 | 변경 제안·명세·설계, 관련 도메인 규칙과 프로젝트 설정 | 요구사항 누락·모호함, DDD 책임·규칙의 일치 여부, 구현 전 해결할 항목과 위치 |
| 완료 검토 | 인수 조건, 변경 파일, 실제 검증 결과·계약·문서 | 조건별 충족/미충족/미검증, 관찰한 증거, 남은 문제, 완료 가능 여부 |

검토 스킬은 보고서를 작성한 사실을 테스트 성공이나 배포 성공으로 바꾸지 않는다. 검토 실행만으로 문서를 자동 승인하거나 코드를 병합하지 않는다. 명세 작성과 구현에는 OpenSpec의 해당 작업 절차 및 이 기반의 체크리스트를 연결한다.

### 10.3 연결된 프로젝트의 모습

다음은 연결 계층을 설명하는 예시이며 모든 도구의 모든 버전에서 그대로 지원되는 경로라고 가정하지 않는다. 구현 시 공식 지원 경로와 생성 결과를 확인해 고정한다.

```text
my-project/
├─ AGENTS.md                         # 공통 안내와 프로젝트 규칙으로 연결
├─ .foundation/
│  ├─ guide.md
│  ├─ skills/                        # 자체 검토 스킬의 관리 원본
│  └─ checklists/
├─ .agents/skills/                   # 이를 인식하는 도구용 스킬 연결·생성본
├─ CLAUDE.md                         # Claude 선택 시 필요한 공통 지침 연결
├─ .claude/skills/                   # Claude 선택 시 필요한 스킬 연결·생성본
├─ docs/                             # 모든 도구가 참조하는 프로젝트 문서
└─ openspec/                         # 모든 도구가 참조하는 현재 명세·변경 기록
```

도구별 진입 파일과 추가 설정은 사용자가 선택한 도구에 필요한 것만 제공한다. 예시 저장소의 `.codex/skills/` 같은 경로를 이름만 보고 그대로 복제하지 않는다. 여러 도구가 한 경로를 읽을 수 있다면 불필요한 별도 폴더를 만들지 않는다.

공통 스킬 원본과 생성 복사본 사이의 경로 대응·기준 해시·생성 도구 버전을 기록한다. 생성 복사본을 사람이 수정했다면 자동 갱신하지 않고 차이를 보고한다. OpenSpec이 소유한 스킬과 이 기반이 제공하는 추가 스킬은 이름과 관리 대상을 구분한다. 같은 `.agents/skills/` 아래에 있더라도 폴더 전체를 교체하지 않는다.

### 10.4 설치·버전과 적용 확인

초기 제안은 프로젝트 범위의 도구 연결이다. 팀원이 같은 지침 버전을 확인할 수 있게 하고, 사용자 전체 환경에 설치하는 방식을 기본으로 강제하지 않는다. 제품 구현 언어와 OpenSpec·검사 도구의 실행 환경은 구분한다.

OpenSpec 내장 스킬을 직접 복제·수정해 별도 버전으로 유지하지 않는다. 프로젝트 맥락과 요구 항목은 지원되는 설정·규칙 확장으로 연결한다. 기본 형식과 충돌하는 부분이 확인되면 구현 전에 지원 버전에 맞춰 조정한다.

OpenSpec CLI·생성 스킬·문서 검사 도구의 검증 버전을 릴리스마다 기록한다. 도구는 관리용 Node.js 환경을 우선 검토하되, 정확한 버전과 추가 패키지는 첫 구현에서 호환성을 확인해 고정한다. 문서 검사에는 가능한 한 별도 의존성을 적게 사용한다.

루트 `AGENTS.md`는 짧은 진입점이다. 공통 `guide.md`와 프로젝트 설정을 읽고, 작업 주제에 필요한 문서만 추가로 읽도록 안내한다. AI별 추가 연결 파일은 선택한 도구에 필요한 경우에만 생성한다. 실제 지원 범위는 검증된 도구·버전만 명시한다.

각 연결에 대해 진입 파일 인식, 스킬 발견 또는 명시적 실행, 공통 입력 참조, 결과 형식 준수와 도구 제약을 확인한다. 파일 존재 확인과 실제 AI 세션에서의 동작 확인을 구분한다. 초기 버전은 실제 사용할 도구 하나를 먼저 검증하며 다른 도구의 연결은 검증 상태를 명시한다. 저장소를 읽을 수 없는 대화형 AI에는 필요한 문서와 작업 조건을 전달하는 안내를 제공하고 자동 연결을 주장하지 않는다.

## 11. 프로젝트 시작 경험

1. 원본 릴리스에서 사용할 버전의 프로젝트 시작용 파일을 받는다.
2. 빈 폴더에 풀고, 제공 파일과 제외된 제작 자료를 확인한다.
3. 프로젝트 이름과 제품 개요·용어·기술 미정 사항을 작성한다.
4. 선택한 AI 도구에 맞춰 안내된 버전의 OpenSpec을 프로젝트 범위로 초기화한다.
5. 첫 기능 변경을 작성하고 명세·설계·작업 목록을 검토한다.
6. 기술을 선택한 뒤 프로젝트별 명령·코드 규칙·검증 범위를 기록하고 실제 개발을 진행한다.

미정 값을 채워진 설정으로 취급하지 않는다. 실행 명령이 없으면 미구성으로 표시하고 기능 명세 작성과 프로젝트 설정의 미정 상태를 구분한다.

원본 저장소를 Fork해 솔루션을 보완하는 사용자는 원본 구조에서 작업한다. 제품 프로젝트를 시작할 때는 동일한 내보내기 산출물을 사용한다. Fork 자체를 초기화 과정에서 파괴적으로 정리하는 기능은 제공하지 않는다.

## 12. 원본 업데이트

초기 버전은 자동 병합보다 **변경 비교와 수동 반영 안내**를 우선 제공한다.

1. 적용할 릴리스의 변경 이력과 호환성 안내를 읽는다.
2. 현재 기반 버전과 기준 해시로 `.foundation/` 직접 수정 여부를 확인한다.
3. 이전·신규 버전의 관리 파일 추가·수정·삭제와 프로젝트 설정에 미치는 영향을 미리 확인한다.
4. 프로젝트 파일과 도구 생성물은 자동 덮어쓰기 대상에서 제외한다. 관리 파일의 지역 수정은 충돌로 보고하며 강제 적용하지 않는다.
5. 관리 파일 변경을 별도 브랜치 또는 명확한 변경 단위로 반영한다. 신규 안내가 프로젝트 규칙과 충돌하면 내용을 검토해 해결한다.
6. 문서 검사와 영향을 받는 프로젝트 검증을 수행한다. 성공한 뒤 버전 기록을 갱신한다.
7. 실패 시 해당 업데이트 변경을 되돌릴 수 있도록 적용 전 상태와 변경 목록을 보존한다.

루트 진입 문서 양식의 개선은 기존 프로젝트에 제안 패치나 이전 안내로 제공한다. 새 양식으로 기존 제품 내용을 교체하지 않는다. 관리 파일 삭제도 버전 차이와 지역 변경을 확인한 명시적 변경으로만 수행한다.

## 13. 초기 자동 검사의 범위

검사 대상 파일 목록을 먼저 정해 제작 문서·예시·프로젝트 문서를 구분한다.

- 배포물에 제작용 문서·예시 제품 내용이 섞이지 않았는지 확인
- 기반 버전·관리 파일 목록·기준 해시 형식 검사
- 저장소 내부 파일 링크의 대상 존재 검사. 초기에는 외부 URL·앵커의 정확성까지 검사한다고 주장하지 않음
- 정해진 명세 필수 항목과 인수 조건 ID 참조의 형식·존재 검사
- 선택한 OpenSpec 버전의 공식 명세 검사 연결

자동 검사는 문서의 존재와 형식 일부를 확인한다. 업무 규칙의 옳고 그름, 코드의 실제 동작, 테스트 증거의 충분함, 모든 AI의 지침 준수는 사람·AI 검토와 실행 검증으로 확인한다.

## 14. 시범 검증과 성공 기준

| 시범 | 확인 내용 | 연결 인수 조건 |
|---|---|---|
| 빈 폴더에서 프로젝트 시작 | 제작 자료 없이 기획·첫 변경 작성 가능 | AC-01, AC-10 |
| 예약 취소 예시 | 규칙·명세·설계·작업·검증의 연결 | AC-02, AC-03, AC-07, AC-09 |
| 별도 세션 인계 | 과거 대화 없이 현재 변경과 검증 상태 파악 | AC-04 |
| AI 도구별 연결 | 선택한 도구에서 공통 지침·스킬의 적용과 결과 형식 확인. 미검증 도구와 지원 차이 표시 | AC-03, AC-04 |
| 서로 다른 기술 설정 두 가지 | 제품 언어·배포가 달라도 공통 규칙 보존 | AC-05 |
| 정상·오류 문서 사례 | 누락 항목과 잘못된 내부 링크 검출 | AC-06 |
| 기반 버전 변경 | 관리 파일 비교·지역 수정 충돌·프로젝트 내용 보존·복구 | AC-08 |

초기 연결 예시와 인계 검토는 문서 수준으로 수행할 수 있다. 실제 제품 코드 구현이나 배포 성공을 대신 증명하지 않는다. 기반 도구의 동작은 별도로 실행 검증한다. 검증에 사용한 OS·관리 도구·AI 버전을 남기고 미검증 조합을 공개한다.

## 15. 설계 제안과 남은 선택

이번 초안의 주요 제안은 한 원본 저장소, 필요한 구성만 내보내는 릴리스, 버전별 공통 폴더와 프로젝트 파일의 분리, 공통 스킬과 AI 도구별 연결, 덮어쓰기 없는 업데이트 안내다. 사용자가 파일명이나 기술 세부를 이미 선택했다고 가정하지 않는다.

명세·검사 형식의 정확한 표현, 해시 목록 스키마, 내보내기 도구의 내부 코드 구조는 구현 계획에서 결정할 수 있다. 제품 목적을 바꾸지 않는 세부 선택은 근거와 함께 기록한다.

저장소 이름·GitHub 소유자·공개 범위는 실제 생성 전에 확인한다. 아직 GitHub 저장소·애플리케이션·도구를 생성하거나 설치하지 않았다.
