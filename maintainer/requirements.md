# 재사용 가능한 SDD 개발 기반 — 요구사항 초안

- 문서 상태: Draft — 검토 전
- 초안 버전: 0.2
- 작성일: 2026-11-18
- 대상: 여러 프로젝트에 복제하여 사용할 문서·협업·AI 작업 기반
- 문서 성격: 지금까지 합의한 방향과 이를 구체화한 제안을 정리한 요구사항 초안. 승인된 최종 규칙이나 구현 완료 기록이 아니다.

## 이 문서와 제공 구성의 구분

이 문서는 공통 기반 자체를 제작·유지관리하기 위한 요구사항이다. 파생 프로젝트의 제품 기획서나 AI 기본 입력으로 제공하지 않는다.

| 구분 | 내용 | 파생 프로젝트에서의 취급 |
|---|---|---|
| 제작·유지관리 문서 | 이 요구사항, 기반 자체의 설계·작업·검증 기록 | 기본 제공 대상에서 제외 |
| 재사용 구성 | 빈 양식, 작성 안내, 공통 작업 규칙, 검토 기준, 필요한 검사 도구 | 프로젝트 시작 시 제공 |
| 작성 예시 | 양식과 규칙의 사용법을 보여주는 가상 제품 사례 | 참고 자료로 구분하며 실제 제품 명세로 사용하지 않음 |
| 프로젝트별 내용 | 해당 서비스의 기획·도메인·기능·기술 선택·실행 결과 | 새 프로젝트에서 작성 |

Fork는 저장소 파일을 함께 가져오므로 이 구분만으로 파일이 자동 제외되지는 않는다. 후속 설계에서 제작 문서의 보관 위치와 필요한 구성만 새 프로젝트에 제공하는 방법을 결정한다. 파생 프로젝트의 기본 문서 탐색과 AI 읽기 경로에는 제작 문서와 예시를 넣지 않는다.

## 1. 목적

개발자와 AI가 바뀌어도 같은 요구사항을 이해하고, 비슷한 깊이의 설계·구현·검증 결과를 만들 수 있는 재사용 기반을 제공한다.

개별 프로젝트는 이 기반에서 시작해 자신의 제품 기획, 도메인, 기술 스택과 배포 방식을 정한다. 원본 기반은 지속적으로 보완하며, 파생 프로젝트가 필요한 개선을 도입할 수 있도록 한다.

결과물의 일관성은 코드가 동일하다는 뜻이 아니다. 요구사항 해석, 문서의 필수 내용, 설계 원칙의 준수, 검증과 완료 증거가 일관되는 것을 뜻한다.

## 2. 합의한 방향

| 항목 | 합의 내용 |
|---|---|
| 개발의 중심 | SDD: 명세를 설계·작업·구현·검증·변경 기록의 기준으로 사용 |
| DDD의 역할 | 명세와 설계를 구체화할 때 용어·업무 규칙·도메인 경계·책임을 정리 |
| 변경 관리 도구 | OpenSpec 활용 |
| 사용자 | 당장은 개인 개발, 여러 팀원과 여러 AI가 사용하는 상황까지 고려 |
| 제공 범위 | 문서·협업·AI 작업 체계 우선 |
| 기술 선택 | 언어·프레임워크·DB·배포 방식은 파생 프로젝트에서 결정 |
| 재사용 | 원본 기반에서 프로젝트를 시작하고 원본도 지속적으로 개선 |

이하의 구체적인 문서 항목, ID, 검증 방식과 초기 범위는 검토를 위한 제안이다.

## 3. 지원할 사용 조건

개인과 팀이 사용할 수 있으며, 사용하는 AI가 바뀌어도 공통 문서와 작업 기준을 유지할 수 있어야 한다.

- 이전 대화에 참여하지 않은 작업자도 현재 명세·작업 범위·남은 작업과 검증 상태를 확인할 수 있게 한다.
- 팀 규모와 사용 도구에 맞게 검토 방식을 선택할 수 있게 한다. 개인 개발에서 형식적인 다인 승인 절차를 강제하지 않는다.
- 개인 개발자·팀원·AI·유지관리자를 별도의 필수 역할로 생성하거나 프로젝트에 고정하지 않는다.
- 파생 프로젝트 기획서의 대상 사용자는 해당 서비스에 맞게 작성한다. 이 기반의 사용 조건을 복제하지 않는다.

## 4. 제공 범위

### 4.1 초기 버전에 포함할 것

1. 새 프로젝트를 시작하는 안내와 작성 순서
2. 기획·범위·핵심 사용자 흐름을 정리하는 양식
3. DDD 용어·업무 규칙·경계·책임을 정리하는 양식과 적용 지침
4. OpenSpec을 사용하는 기능 명세·변경·설계·작업 관리 절차
5. 중요한 결정의 배경과 대안을 기록하는 ADR 양식
6. 사람과 AI의 공통 작업 원칙, 프로젝트별 규칙을 연결하는 방식
7. 구현·검토·검증·완료 기준과 PR 작성 양식
8. 서로 연결된 문서 작성 예시와 검토 체크리스트
9. 프로젝트별 기술·실행·테스트·배포 설정의 작성 지침
10. 기반 버전·변경 이력·파생 프로젝트 업데이트 안내
11. 초기 범위에서 확실하게 검사할 수 있는 문서 자동 검사

### 4.2 초기 버전에 포함하지 않을 것

- 실행 가능한 프론트엔드·백엔드 애플리케이션
- 특정 언어의 패키지 구조, 프레임워크, DB·클라우드의 강제 선택
- 제품 코드의 빌드·배포 파이프라인과 실제 인프라
- 모든 프로젝트에 DDD의 모든 패턴, MSA, CQRS 등을 일괄 적용하는 규칙
- 모든 AI 제품의 전용 설정과 자체 AI 실행 플랫폼
- 파생 프로젝트를 자동으로 일괄 수정하는 업데이트 서비스

문서 검사용 도구에는 별도 실행 환경이 필요할 수 있다. 이 환경은 제품 구현 언어와 구분해 명시한다.

## 5. 기본 작업 흐름

1. **프로젝트 시작:** 해결할 문제, 사용자, 성공 기준, 첫 출시 범위와 제외 범위를 작성한다.
2. **공통 맥락 정리:** 핵심 용어와 업무 흐름, 도메인 경계 후보를 정리한다. 불확실한 내용은 미정으로 표시한다.
3. **변경 제안·명세:** 개발할 기능 또는 변경의 목적·범위·기대 동작·인수 조건을 작성한다.
4. **설계:** DDD 관점의 책임·규칙·경계를 반영하고, 필요한 인터페이스·데이터·실패 처리를 설계한다.
5. **작업 분해:** 명세·설계와 연결된 구현·검증 작업을 정의한다.
6. **구현:** 명세와 프로젝트 규칙을 기준으로 작업한다. 중요한 요구사항 변경은 명세·설계·작업 목록에 함께 반영한다.
7. **검토·검증:** 인수 조건과 실제 변경을 대조하고, 실행 결과와 미검증 항목을 기록한다.
8. **변경 마무리:** 현재 명세에 변경을 반영하고, 작업 기록을 보관하며 관련 Issue·PR·CI를 연결한다.
9. **배포·운영:** 기능 구현 완료와 구분해 배포·복구·운영 결과를 기록한다. 운영에서 발견한 문제는 다음 변경으로 연결한다.

이 흐름은 전체 기능을 처음부터 상세 설계하는 절차가 아니다. 프로젝트 방향을 정한 뒤 기능·변경 단위로 반복한다. 단순 수정은 필요한 항목만 사용하고 복잡한 변경은 설계를 확장한다.

## 6. 기능 요구사항

| ID | 요구사항 | 확인 가능한 결과 |
|---|---|---|
| BASE-01 | 시작 안내는 처음 사용할 사람이 읽을 문서와 작성 순서를 안내해야 한다. | 새 사용자가 시작 문서에서 첫 기획 양식과 다음 단계에 접근할 수 있다. |
| BASE-02 | 기획 양식은 문제·대상 사용자·목표·성공 기준·범위·제외 범위·미정 사항을 포함해야 한다. | 서로 다른 제품의 기획을 같은 기본 항목으로 기록할 수 있다. |
| BASE-03 | 문서 종류마다 책임과 원본 위치를 정의해야 한다. | 업무 규칙·기능 동작·API 계약·작업 상태·실행 증거의 원본을 구분할 수 있다. |
| BASE-04 | 기능 명세는 목적·포함/제외 범위·행위자/권한·정상/실패 시나리오·인수 조건·미정 사항을 다뤄야 한다. | 구현자 외의 검토자가 명세를 읽고 성공·실패 결과를 판단할 수 있다. |
| BASE-05 | DDD 지침은 용어·업무 규칙·경계·책임을 설계와 연결해야 한다. | 관련 규칙이 명세 또는 설계에 참조되고, 사용하지 않은 DDD 패턴 때문에 작업을 막지 않는다. |
| BASE-06 | 설계 기록은 영향 범위·중요한 선택·계약·데이터·검증 접근을 다뤄야 한다. | 해당하는 변경에서 동시성·중복 요청·외부 실패·호환성의 처리 방식을 확인할 수 있다. |
| BASE-07 | 작업 목록과 검증은 해당 명세의 인수 조건으로 추적할 수 있어야 한다. | 인수 조건별 구현 작업과 테스트 또는 수동 확인 방법을 찾을 수 있다. |
| BASE-08 | 명세·계획·작업·구현·배포의 상태를 혼동하지 않아야 한다. | 명세 승인이나 작업 체크만으로 테스트·CI·배포 성공을 주장하지 않는다. |
| BASE-09 | 사람과 AI는 공통 지침과 동일한 프로젝트 기준을 사용해야 한다. | AI별 설정에 제품 규칙을 별도로 복제하지 않고 공통 원본을 연결한다. |
| BASE-10 | 새 작업자는 대화 이력 없이 현재 작업을 재개할 수 있어야 한다. | 변경 식별자, 관련 브랜치/커밋, 남은 작업, 미정 사항, 검증 증거의 위치가 제공된다. |
| BASE-11 | 프로젝트별 기술 선택과 실행 명령을 별도로 정의해야 한다. | 언어·배포 방식이 다른 프로젝트가 공통 원칙을 수정하지 않고 설정할 수 있다. |
| BASE-12 | 현재 명세와 검토 중인 변경, 완료한 변경 기록을 구분해야 한다. | 과거 기록을 현재 기준으로 오인하지 않고 기능의 최신 동작을 찾을 수 있다. |
| BASE-13 | 원본 개선을 파생 프로젝트에 도입하는 절차가 있어야 한다. | 사용 중인 기반 버전, 변경 영향, 적용·검증·복구 방법을 확인할 수 있다. |
| BASE-14 | 문서 검사와 내용 검토의 경계를 명시해야 한다. | 링크·필수 항목 등의 검사와 업무 규칙의 타당성·구현 일치 검토가 구분된다. |
| BASE-15 | 제작용 문서·참고 예시와 프로젝트에서 사용할 구성을 구분해야 한다. | 새 프로젝트의 기본 읽기 경로에 기반 자체의 기획·요구사항·예시 제품 규칙이 포함되지 않는다. |

인수 조건 ID의 구체적인 표기와 OpenSpec 필드 연결 방식은 후속 설계에서 정한다. OpenSpec 기본 산출물과 별도의 동일 목적 문서를 중복 생성하지 않는다.

## 7. 결과물 편차를 줄이는 기준

### 7.1 필수 항목과 조건부 항목

명세의 기본 항목은 공통으로 유지한다. 데이터 변경, 동시성, 보안, 외부 연동, 배포 전환 같은 항목은 해당할 때 확장한다. 해당하지 않는 항목은 간단한 사유로 표시할 수 있게 한다.

### 7.2 양식·예시·검토 기준을 함께 제공

각 핵심 양식에는 항목의 목적, 작성 예시와 검토 질문을 제공한다. 예시의 값이나 제품 규칙은 프로젝트 기본 정책으로 취급하지 않는다.

### 7.3 관찰 가능한 인수 조건

“취소가 정상 동작한다” 대신 “취소 불가 상태에서 요청하면 거절되며 기존 상태가 유지된다”처럼 결과를 판단할 수 있게 작성한다.

### 7.4 프로젝트 내부의 구현 규칙

공통 기반은 모든 언어의 코드 구조를 고정하지 않는다. 파생 프로젝트는 의존성 방향, 오류 처리, 테스트와 코드 스타일 등을 결정하고 기록한다. 팀원과 AI는 그 프로젝트 안에서 같은 규칙을 따른다.

### 7.5 변경 크기에 비례하는 절차

단순 문구 수정과 신규 결제 기능에 같은 문서량을 요구하지 않는다. 가벼운 변경에서도 영향 범위·필요한 검증·실제 결과를 확인하며, 상세 설계가 필요한 조건은 지침으로 정한다.

## 8. 기록의 책임과 변경 처리

| 기록 종류 | 소유할 내용 |
|---|---|
| 기획 | 제품 목적·사용자·성공 기준·출시 범위 |
| 도메인 | 용어·공통 업무 규칙·업무 경계와 책임 |
| 현재 기능 명세 | 사용자에게 제공해야 하는 동작·시나리오·인수 조건 |
| 기계가 읽는 계약 | 해당 프로젝트가 채택한 API·이벤트 등의 정확한 인터페이스 |
| 변경 기록 | 이번 변경의 이유·범위·명세 변경분·설계·작업 목록 |
| ADR | 여러 기능이나 장기 유지에 영향을 주는 중요한 설계 결정과 이유 |
| Issue·PR·CI | 협업 범위, 검토, 실제 실행 결과와 증거 |
| 운영 기록 | 배포·롤백·장애 대응·관측 결과 |

작업 체크리스트와 협업 보드의 역할을 구분해 같은 진행 상태를 수동으로 반복 기록하지 않는다. 세부 소유 위치와 상태 전환 규칙은 후속 설계에서 확정한다.

문서끼리 충돌하면 충돌 내용을 기록하고 해당 원본을 정정한다. 문서와 구현이 다르면 의도한 변경인지 구현 오류인지 판단한다. 명세 수정만으로 구현을 정당화하거나 현재 코드만으로 요구사항을 덮어쓰지 않는다.

## 9. 기술 독립성과 도구 운영

- 특정 애플리케이션 코드나 배포 환경 없이 기반 자체를 사용할 수 있어야 한다.
- 제품 언어와 별개로 OpenSpec·문서 검사에 필요한 도구와 설치 범위를 명시한다.
- 지원하는 도구 버전과 업데이트 방법을 기록한다. 모든 AI와 버전을 동일하게 지원한다고 주장하지 않는다.
- 공통 AI 지침은 짧은 진입점과 필요한 상세 문서 연결로 구성한다.
- AI 전용 연결 파일은 필요한 도구에만 추가하고, 공통 규칙과 중복되지 않도록 한다.
- 원본 공통 파일과 프로젝트별 파일·설정을 구분해 업데이트 충돌을 줄인다.
- 공통 기반의 개선과 개별 서비스의 정책 변경을 구분한다.

## 10. 초기 버전 인수 조건

| ID | 인수 조건 | 검증 방법 |
|---|---|---|
| AC-01 | 빈 프로젝트에서 기획 문서와 첫 기능 변경을 작성할 수 있다. | 시작 안내를 따라 시범 프로젝트를 작성하고 막힌 지점을 기록한다. |
| AC-02 | 하나의 예시에서 기획·도메인 규칙·명세·설계·작업·검증 기록이 연결된다. | 문서 간 연결과 인수 조건별 검증 방법을 검토한다. |
| AC-03 | 정상·권한 거부·상태 충돌 등 예시의 주요 시나리오가 같은 기준으로 설명된다. | 작성 예시와 검토 체크리스트를 대조한다. |
| AC-04 | 다른 작업자가 기존 대화 없이 작업 범위와 완료 조건을 파악할 수 있다. | 별도 세션 또는 협업자 검토로 인계 가능성을 확인한다. 실제 검증 대상을 기록한다. |
| AC-05 | 서로 다른 두 기술·배포 선택을 공통 규칙 변경 없이 표현할 수 있다. | 두 개의 프로젝트 설정 예시를 비교한다. 실제 애플리케이션 구현은 요구하지 않는다. |
| AC-06 | 필수 명세 항목 누락과 잘못된 저장소 내부 문서 링크를 검출할 수 있다. | 정상 예시와 의도적으로 오류를 넣은 예시에 문서 검사를 실행한다. 검사 범위를 명시한다. |
| AC-07 | 실행하지 않은 테스트나 배포는 완료 증거로 기록되지 않는다. | 성공·실패·미실행을 포함한 검증 기록 예시와 완료 체크리스트를 검토한다. |
| AC-08 | 원본 업데이트를 적용해도 프로젝트별 내용이 보존된다. | 공통 양식의 버전 변경을 시범 적용하고 프로젝트 설정·문서 보존 및 복구 경로를 확인한다. |
| AC-09 | 현재 명세와 완료한 변경 이력을 구분할 수 있다. | 시범 변경을 마무리하고 명세 반영·기록 보관 상태를 확인한다. |
| AC-10 | 프로젝트 시작 결과에 기반 제작용 요구사항과 가상 제품 내용이 실제 프로젝트 기준으로 들어가지 않는다. | 제공 파일 목록과 기본 문서·AI 읽기 경로를 검토한다. |

실제로 시범 검증한 도구·버전·조건과 미검증 범위를 결과에 기록한다. 한 AI에서의 검증을 모든 AI에서의 호환성 증거로 확대하지 않는다.

## 11. 후속 설계에서 결정할 사항

| 항목 | 현재 제안 | 결정할 내용 |
|---|---|---|
| 이름·저장소 | 미정 | 기반의 이름, 소유 계정과 공개 범위 |
| 배포 형태 | GitHub 저장소 | Fork와 Template의 특성을 비교해 초기 배포·업데이트 방식 선택 |
| OpenSpec 구성 | 기본 구조를 우선 활용 | 버전·설치 범위·기본 절차와 필요한 조정 |
| 실제 파일 구조 | 미정 | 공통 파일·프로젝트 파일·예시의 경계 |
| 문서 검사 | 최소한의 확실한 검사부터 | 실행 환경, 명세 항목·링크 검사 범위와 CI 연결 |
| 초기 AI 검증 | 공통 지침을 기본으로 검증 | 실제 검증할 도구와 추가 연결 설정 |
| 시범 기능 | 작은 업무 기능 | 명세·DDD·오류 처리·검증을 보여줄 예시 선정 |
| 협업 검토 | 개인·팀 사용 모두 고려 | 개인 자체 검토와 팀 리뷰의 구분, 적용 조건 |

이 항목들이 모두 정해져야 초안을 읽을 수 있는 것은 아니다. 실제 파일 제작과 검증에 필요한 순서대로 결정한다.
