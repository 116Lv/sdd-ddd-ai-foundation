# 검토 스킬 평가

명세·설계 검토와 변경 완료 검토의 기대 출력을 정리한다. 반복 평가에서는 같은 입력을 각기 새 AI 세션에 주고, 기본 응답과 원본 스킬을 읽은 응답을 비교한다. 제품 명세와 실행 결과는 가상 입력이다.

평가 대상은 [명세·설계 검토 스킬](../../distribution/managed/skills/foundation-spec-review/SKILL.md.template)과 [완료 검토 스킬](../../distribution/managed/skills/foundation-completion-review/SKILL.md.template)이다.

## 사례와 기대 출력

### 완전한 변경 · 예시

`rename-draft`는 초안 소유자에게만 제목 변경을 허용한다. 제안은 해당 범위를 정하고, 명세에는 소유자의 변경 성공과 비소유자의 거절 및 제목 유지가 각각 `[AC-001]`, `[AC-002]`로 정의되어 있다. 설계는 상태 변경 전에 소유권을 확인하는 위치를 설명한다. 구현·검증 작업을 해당 AC에 연결했다. 현재 커밋의 구현과 아래 CI 실행 결과가 제공됐다고 가정한다.

기대하는 명세 검토는 확인 범위와 발견 사항이 없음을 기록한다. 기대하는 완료 검토는 다음과 같다.

| AC ID | 상태 | 증거 | 남은 문제 |
| --- | --- | --- | --- |
| AC-001 | 충족 | 가상 CI 결과 `rename-draft / owner-renames`에서 소유자 요청 성공과 새 제목 저장 확인 | 없음 |
| AC-002 | 충족 | 가상 CI 결과 `rename-draft / non-owner-denied`에서 비소유자 거절과 기존 제목 유지 확인 | 없음 |

변경 범위에 필요한 검증이 모두 확인됐다는 가정에서 전체 판정은 `완료`다.

### 사례 A · 권한 규칙 누락

예약 소유자만 취소할 수 있지만, 명세에는 예약 ID로 상태를 `CANCELLED`로 바꾸고 HTTP 200을 반환한다는 내용만 있다. 설계는 좌석 배정 변경 뒤 환불 요청을 설명한다. 취소 후 재요청이 가능하고 환불 응답은 타임아웃될 수 있다. 작업 발췌에는 API 구현과 정상 취소 검증이 있다.

기대하는 명세 검토는 `근거 위치 / 분류 / 발견 사항과 영향 / 필요한 결정·수정`으로 보고한다. 소유권 규칙과 명세의 불일치, 비소유자 거절과 부수 효과 방지, 재요청·동시 요청의 중복 효과, 환불 타임아웃 후 상태와 복구 책임, AC와 작업 연결의 공백을 근거 위치와 함께 지적한다. 제공받은 범위를 표시하고 구현 전에 정할 사항을 남긴다.

### 사례 B · 제품 테스트 전부 미실행

완료를 요청한 예약 취소 변경에는 비소유자 거절과 재시도 시 중복 환불 방지라는 두 AC가 있다. 모든 작업이 체크되어 있고 Markdown 링크 검사는 통과했다고 제시되었다. 제품 테스트와 배포는 실행되지 않았다.

| AC ID | 상태 | 증거 | 남은 문제 |
| --- | --- | --- | --- |
| AC-001 | 미검증 | 비소유자 거절 실행 결과 없음 | 비소유자 요청의 거절과 부수 효과를 확인 |
| AC-002 | 미검증 | 재요청의 환불 횟수를 확인한 기록 없음 | 재요청 결과와 환불 횟수를 확인 |

기대하는 판정은 `완료 보류`다. 작업 상태, 문서 검사, 제품 테스트와 배포의 실행 여부를 각각 기록한다.

### 사례 C · 실행 결과가 기대와 다른 제품 AC (가상)

다음은 가상 변경 `rename-draft`의 다른 실행을 가정한 예시다. 예상은 비소유자 거절과 기존 제목 유지다. 가상 실행 로그에는 응답 200과 다른 사용자가 지정한 제목 저장이 기록됐다.

| AC ID | 상태 | 증거 | 남은 문제 |
| --- | --- | --- | --- |
| AC-001 | 충족 | 가상 로그 `rename-draft / owner-renames`에서 소유자 요청 뒤 새 제목을 조회 | 없음 |
| AC-002 | 미충족 | 가상 로그 `rename-draft / non-owner-denied`에서 비소유자 요청을 거절해야 했으나 200을 반환했고 제목도 변경됨 | 소유권 검사 후 같은 거절·상태 보존 검증을 재실행 |

전체 판정은 `완료 보류`다. 사례 B의 미실행 행은 `미검증`이며 이 사례처럼 기대와 어긋난 실행 결과가 있으면 `미충족`이다. 예약 취소 예시의 네 제품 AC는 모두 미검증이다.

### 사례 D · 시나리오 없는 변경 (가상)

`rename-policy` 작업은 `(CHANGE: rename-policy)`를 참조하고 모두 체크되어 있다. 제안은 정책 이름만 바꾸기로 했고 diff의 RENAMED에는 이전·새 이름이 있다. 문서 구조 검사는 통과했으나 기존 참조가 새 이름으로 해석되는지 확인한 기록은 없다.

| AC ID | 상태 | 증거 | 남은 문제 |
| --- | --- | --- | --- |
| 해당 없음 (rename-policy) | 미검증 | 제안·diff에서 이름 변경 확인. 기존 참조 조회 실행 결과 없음 | 해당 변경본에서 기존 참조가 새 이름을 찾는지 실행하고 결과를 기록 |

전체 판정은 `완료 보류`다. 시나리오가 있는 혼합 변경이라면 ADDED·MODIFIED의 각 AC를 별도 행으로 확인한다.

## 실제 AI 실행 결과

사례 A·B를 각각의 평가 세션에 같은 입력으로 제공했다.

- 스킬 작성 전 기준 세션은 소유권·중복 처리·타임아웃 문제를 발견했고, 테스트 실행 증거가 없는 변경의 완료를 보류했다. AC별 필요한 증거를 제시했으나, `상태 / 증거 / 남은 문제`를 행마다 같은 형식으로 기록하지 않았다.
- 작성 후 독립 세션은 두 스킬 원본과 해당 체크리스트를 명시적으로 읽었다. 사례 A는 근거 위치가 있는 네 열의 발견 사항, 확인하지 못한 입력과 구현 전 결정 사항을 반환했다. 사례 B는 두 AC를 각각 `미검증`으로 표시하고 증거와 남은 문제를 기록했으며 `완료 보류`로 판정했다. 작업 체크, 문서 검사, 제품 테스트와 배포도 각각 보고했다.

작성 후 평가는 스킬을 명시적으로 제공했을 때의 검토 형식과 판단을 확인했다. 네이티브 설치·자동 탐색, 다른 AI 도구에서의 적용, 제품 테스트 및 배포는 평가 범위 밖이다.

평가 뒤 명세 체크리스트에 설계의 영향 범위·중요한 선택·검증 방법을 확인하는 항목과 요구사항 예시의 SHALL·MUST 안내를 추가했다.

## 텍스트 검토 결과

두 스킬의 입력 경로, 체크리스트 참조, 발견 사항 및 AC별 증거의 출력 형식을 원본에서 확인했다. 완전한 변경 예시는 문서로 기대 출력을 확인했다. 사례 C·D의 네 열 출력과 판정을 수정된 스킬 및 체크리스트에 대조해 텍스트로 검토했다. 앞의 세션 결과는 당시 스킬과 입력 A·B에 해당한다. 완전한 변경 예시와 C·D로 수정된 스킬을 네이티브 AI 세션에서 실행하거나 제품 테스트를 수행한 기록은 없다.
